# 代码审查

## 前置

- **显式启用**：约定仅在用户 **@ 本 skill** 或明确要执行代码审查时再按本流程执行，避免日常对话误跑审查步骤。
- 审查对象为**实际变更**；若当前工作区是 git 仓库，优先用命令行结论与 diff 定界（见「执行顺序」第 1 步）。

## 何时使用

- 用户提供了 diff、`git` 范围、文件路径、PR 描述，或笼统要求「审查最近改动」。
- 优先以**实际变更**为审查对象；若无 diff，则审查用户点名的文件/目录。

## 执行顺序

1. **建立上下文**：确认审查范围（用户给出的文件列表、PR 描述或 diff）。
   - 若用户仅说「审查最近改动」等**未点名文件**：在**仓库根**先执行 **`git status`**。**未跟踪（Untracked）** 路径不会出现在 `git diff` 中，须将 `git status` 列出的未跟踪文件/目录一并纳入审查（对相关内容 `Read`），再配合 `git diff`（工作区已跟踪）、`git diff --staged`（暂存区）或与默认分支的对比（如 `git diff main...HEAD`）覆盖已跟踪变更。
   - 若上述范围内**既无未跟踪项**，且**已跟踪**工作区/暂存区/相对默认分支也**均无 diff**，则视为无本地变更，说明情况并停止或请用户指定路径。
   - 若**不是** git 仓库或无法执行 git：以用户点名的文件/目录为准；未指定则请用户给出范围。
   - 确定范围后，必要时 `Read` 被调用的模块、路由、`http` 与相关 `services`。
2. **对照项目约束**：分层（禁止裸 axios）、`@/` 别名、路由注册、环境变量 `VITE_*`、敏感信息不入库。细则见 [reference.md](reference.md)。
3. **分维度记录**：每条发现注明**位置**（文件 + 大致行号或符号名）与**理由**；不确定时写为「需确认」并给出验证方式。
4. **输出**：按下方格式给出摘要与分级项；避免泛泛而谈或只复述 diff。

## 审查维度（速查）

| 维度            | 关注点                                                                     |
| --------------- | -------------------------------------------------------------------------- |
| 正确性与边界    | 空值、异步竞态、错误路径、路由与权限假设                                   |
| 安全与合规      | 密钥/token、XSS（`dangerouslySetInnerHTML`）、不可信 URL、日志中的敏感字段 |
| 分层与 API      | 经 `http`、逻辑在 `services/`、页面/组件不堆 API 细节                      |
| TypeScript      | 公共类型、Props 类型显式声明、避免滥用 `any`                               |
| React / Hooks   | `useEffect` 清理、依赖数组完整性、Hook 边界与分层、组件行数限制            |
| Zustand / Store | selector 粒度、避免不必要的全量订阅、store 职责边界与副作用归属            |
| 样式与 UI       | Tailwind + `cn()`、shadcn/ui 一致性、可访问性（语义、焦点）                |
| 可观测性        | 错误是否可感知；是否与 `http` 拦截器策略一致                               |

## 输出格式

先给**一段摘要**（是否建议合并、最大风险点），再列条目：

- **必须修复**：阻塞合并或高风险的缺陷、违规分层、安全与数据问题。
- **建议**：可读性、一致性、小重构、边界情况。
- **可选**：风格微调、后续优化、测试补强建议。

每条使用列表，包含：**位置** → **问题** → **建议**（必要时给示例思路，避免大段无必要代码）。
